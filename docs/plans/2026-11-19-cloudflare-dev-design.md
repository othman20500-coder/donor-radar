## الخيارات
1. Workers مع D1 جديدة وR2 خاص: يناسب مشروع Cloudflare مستقلًا، لكنه يتطلب تحويل استدعاءات SQLite المتزامنة إلى غير متزامنة، وإعادة تصميم العمليات الذرية والتحقق من تعارض التعديلات. هذا هو المقترح المتسق مع المسار الذي نوقش مع المستخدم.
2. Workers مع Durable Object وSQLite مدمجة وR2 خاص: أقرب إلى المعاملات المتزامنة الحالية، لكنه يضيف تنسيقًا مركزيًا وتغييرًا في نموذج قاعدة البيانات الذي سبق اقتراحه.
3. Containers: أقرب لخادم Node الحالي، لكن القرص مؤقت افتراضيًا، فلا يحل حفظ SQLite دون تصميم إضافي للتخزين. غير مقترح لهذه المرحلة.

## تصميم الخيار الأول
- Worker مقترح اسمه donor-radar-v13-dev، على workers.dev فقط؛ الاسم والرابط النهائيان رهن التوافر بالحساب.
- قاعدة D1 جديدة donor-radar-v13-dev؛ لا استيراد للمستخدمين أو الجلسات أو بيانات التشغيل من الإنتاج.
- حاوية R2 خاصة عند الحاجة للمرفقات والنسخ المنطقية، دون عنوان عام؛ تنزيل الملفات خلف المصادقة وقائمة السماح.
- الحفاظ على الواجهة الحالية وشاشة الدخول والأدوار admin/editor/viewer وقواعد صلاحيات السجلات.
- تكييف API إلى Request/Response مع Origin وCSRF وملفات تعريف ارتباط Secure/HttpOnly/SameSite وفحص الجلسة والحساب عند كل تعديل.
- تقييم تكلفة scrypt الحالية في بيئة Workers قبل اعتمادها. لا خفض عشوائي لقوة حماية كلمات المرور؛ أي تغيير للخوارزمية يختبر ويقتصر على حسابات الاختبار الجديدة.
- حماية آخر مدير نشط، وإبطال الجلسات عند تغيير الدور أو كلمة المرور، وتحديد محاولات الدخول في تخزين مشترك.
- إعادة تصميم المعاملات وكتابة السجل والتدقيق ومراجعة الإصدار كوحدة ذرية؛ اختبار سباق مستخدمين قبل القبول.
- إضافة جداول V13 للأرصاد والسياسات والفرص والأدلة والمراجعات. لا اعتماد تلقائي للتواريخ أو الفرص.
- مراجعة تفعيل الاكتشاف ومسارات مراجعة الأدلة؛ الواجهة الحالية لا توفر دورة V13 كاملة.
- جالب المصادر يقتصر على روابط HTTPS رسمية محددة ومراجعة. منع التحويلات، حد حجم ومدة، تشغيل يدوي، ومصدر واحد أولًا. لا نقل آلية DNS الخاصة بـNode إلى Workers دون اختبار مكافئ لحماية SSRF.
- مراجعة robots وشروط الاستخدام وتوثيق الرابط والتاريخ والنتيجة قبل إتاحة الاتصال لكل مصدر. المنع أو عدم وضوح الإذن يبقي المصدر معطلًا.
- لا مهام مجدولة ولا رسائل ولا تنبيهات خارجية في اختبار القبول الأول.

## خطة التنفيذ والاختبار
1. حفظ نقطة البداية والنسخ الأصلية (تم للكود والحزمة).
2. اعتماد مسار التكييف، ثم إنشاء فرع تطوير محلي مستقل؛ لا دفع إلى main ولا نشر تلقائي.
3. فحص قائمة محتويات نسخة cPanel فقط، ثم استخلاص أصول الواجهة المطلوبة انتقائيًا عند الحاجة؛ عدم استيراد radar-data أو config.json أو قواعد SQLite أو الحسابات.
4. كتابة اختبارات سلوك المصادقة والصلاحيات والسجلات أولًا، ثم تكييف التخزين وAPI وبناء الواجهة من المصدر.
5. دمج V13 مع اختبارات رفض المستخدم غير المسؤول وCSRF والسياسات والأدلة والتكرار وحد الفحص.
6. اختبار محلي في محاكي Cloudflare: دخول صحيح وخاطئ، تغيير كلمة المرور، خروج وإبطال الجلسة، الأدوار الثلاثة، تعارض تحديثات، النسخ والاستعادة في قاعدة اختبار ثانية، حماية المرفقات.
7. إتاحة اتصال Cloudflare بطريقة تسجيل دخول رسمية؛ لا كلمات مرور أو رموز وصول في المحادثة أو Git. لم يوجد اتصال جاهز في هذه الجلسة.
8. إنشاء الموارد الجديدة فقط، وتسجيل معرفاتها للتحقق من عزلها، ثم نشر نسخة التطوير وإعادة اختبارات HTTP والمتصفح.
9. مراجعة سياسة مصدر رسمي وتنفيذ طلب محدود وتوثيق النتيجة؛ معالجة الأعطال وإعادة الاختبارات المتأثرة.
10. إصدار تقرير قبول يميز الناجح والفاشل وغير المختبر، مع رابط التطوير وخطة الرجوع. إبقاء الإنتاج والنطاق الرئيسي خارج النشر.

## معايير القبول
- لا يعتمد التطبيق على ملفات قاعدة محلية مؤقتة.
- لا وصول للصفحات أو المرفقات أو API المحمية دون جلسة مناسبة.
- لا تعديل من viewer، ولا إدارة حسابات أو رصد من غير admin.
- رفض Origin وCSRF غير الصالحين، وإبطال الجلسات كما في السلوك الأصلي.
- لا فقد بيانات عند تعارض تحديثات أو إعادة تشغيل الخدمة.
- لا رصد قبل مراجعة المصدر، ولا اعتماد آلي للفرص أو التواريخ.
- نجاح استعادة نسخة تجريبية إلى قاعدة ثانية، مع دليل مستقل.
- نجاح الفحص الحي المحدود موثق، ولا يخلط مع نجاح المحاكاة.
